The first thing almost everyone does with the Model Context Protocol is wrap an existing API. You have a service with fifteen endpoints, you expose fifteen tools, you point a model at it, and the demo works. It feels like a plugin system, and plugin systems are a solved shape — register a capability, the host calls it, done.

That framing is what makes the second week hard. A plugin is invoked by a program that knows exactly what it wants. A tool over MCP is invoked by a model that is *inferring* what it wants from a text description you wrote, then reading the result and deciding what to do next. Those are not the same contract, and the difference shows up as an agent that loops.

## The consumer is a reader, not a caller

A conventional API's job is to be unambiguous to a compiler. A tool's job is to be unambiguous to a reader who has seen only its description and has to choose it over eleven similar-looking siblings, with no ability to ask you a question.

This changes what "good design" means. `search(query, filters, options)` is a perfectly reasonable function signature and a poor tool. What are valid filters? What happens if I pass none? Is `options` where the pagination lives? A human integrating against it reads your docs once and remembers. A model re-derives the answer from your description on every single call, and where the description is thin it guesses.

The rewrite that fixes this is usually decomposition. Not one `search` with a mode parameter, but `search_customers_by_name` and `search_orders_by_date`, each with a description that says what it is for, what it returns, and — the part everyone omits — **when not to use it**. Fewer parameters, more tools, each one obvious in isolation.

<Feedback variant="info" title="The test I apply to a tool description">
Could a competent new colleague, given only this description and no access to me, pick the right tool for a task and construct a valid call on the first attempt? If not, the model will not either — it just fails more confidently.
</Feedback>

## Errors are a control-flow instruction

In an ordinary integration, an error is something a human reads in a log. In an agent loop, the error string goes straight back into the model's context and becomes the sole basis for its next decision. It is not a diagnostic. It is an instruction, and you are writing it.

`400 Bad Request` tells the model nothing, so it retries the identical call, gets the identical error, and you have built a loop. `Error: invalid date format` is better but still incomplete, because it does not say what the model should do instead.

What actually breaks the loop is an error that contains the correction: *invalid date format "next tuesday" — this parameter takes ISO 8601, e.g. 2026-09-17*. Now the failure is self-correcting on the next turn, and the difference between those two strings is the difference between a tool that recovers and a tool that burns a context window.

The same logic applies to empty results. `[]` is ambiguous — did the query fail, or is the answer genuinely nothing? A model faced with that ambiguity tends to assume it made a mistake and retry with variations. *No orders found for customer 4021 in the last 30 days. The customer exists.* ends the sequence, because it distinguishes "no data" from "wrong call".

## Every response is a bill against the context window

A REST endpoint that returns forty fields is being thorough. A tool that returns forty fields has spent several hundred tokens of the model's finite working memory, and it will do it again on the next call, and the one after.

This inverts a habit. The right default for a tool response is the *smallest* payload that answers the question, not the most complete representation of the resource. Return the five fields that matter. Offer a separate tool for the full record, so the expensive version is opt-in and the model can choose it when it needs to.

The compounding case is worse than the single case. An agent that makes six tool calls before answering has spent the sum of six responses, and if each is verbose, the model is now reasoning over a context that is mostly stale JSON from four steps ago. Truncating tool output is not a hack — it is the responsible default for a resource that is shared across the whole trajectory.

<Feedback variant="warning" title="Pagination is a tool-design problem, not an API problem">
Returning 500 rows because that is what the underlying query returned will blow the context and produce worse answers than returning 10 with a note that more exist. The tool layer is where that judgement belongs; do not pass the database's opinion straight through.
</Feedback>

## Statelessness is what makes it composable

The strongest argument for MCP being a protocol rather than a plugin API is that it forces a discipline plugin systems usually skip: each call has to make sense on its own.

An agent's trajectory is not guaranteed. It may call your tool, wander off to three others, come back, or be interrupted and resumed in a different process. A tool that quietly depends on having been called before — an implicit session, a cursor held in memory, a "current directory" — works perfectly in the happy path and produces baffling behaviour the moment the sequence varies. And the sequence always varies, because a model chose it.

Make state explicit in the arguments. If the tool needs a session, the session identifier is a parameter, returned by whatever created it. This looks more verbose and is the reason the tool still works when the agent does something you did not anticipate.

## What I would tell someone wiring up their first server

- Expose fewer tools than you have endpoints. One tool per *task*, not per route.
- Write the description for a reader who cannot ask questions, and say when not to use it.
- Make every error message contain the correction, not just the complaint.
- Return the smallest useful payload; make the full record a separate call.
- Never depend on call order. Put the state in the arguments.
- Read your own agent's transcripts. The loops are obvious once you look, and invisible until you do.

MCP standardises the transport, which is genuinely valuable and also the least interesting part. The design work it does not do for you is the part that decides whether your agent finishes the task or spends thirty turns rediscovering the date format. That work is not plugin registration. It is API design for a consumer that reads.
